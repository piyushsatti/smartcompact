# The State of the Art in LLM Agent Context Management and Session Self-Management: A Survey for "Smart Compact"

## TL;DR

- Most of the machinery Smart Compact needs already exists as commodity components: lifecycle-hook capture (claude-mem, Mem0), tiered in-context/out-of-context memory (Letta/MemGPT), scoped state separation (Google ADK, LangGraph), and structured-state-with-precedence handoff (OpenAI's cookbook). What is NOT yet solved, and where Smart Compact can genuinely contribute, is intent-driven compaction triggering (compacting on task/goal boundaries rather than token thresholds) and the reliable preservation of session-scoped behavioral constraints across the compaction boundary, which current compactors lose almost entirely.
- The evidence for the core premise is strong: compaction is lossy in measurable, consequential ways. Per "Lost in Compaction" (arXiv 2608.11242), "current compactors retain only 17% of injected SCs on average, and most perform worse than running the same task without compaction," while a dedicated extractor reaches "over 90% retention." Factory.ai's probe evaluation found even its best method scored only 2.45/5 on tracking which files were created/modified/examined. "Context rot" is real and universal across models. This justifies structured state handoff over heuristic summarization.
- The model-size-dependent strategy question (question 3) is genuinely under-studied. Benchmarks (RULER, NoLiMa, LIFBench) consistently show smaller models hitting effective-context and instruction-following-stability walls earlier than larger same-family models, but the effect is noisy and often dominated by training recipe rather than raw parameter count. No research prescribes context-management strategy as a function of model size; only practitioner heuristics exist. Smart Compact should treat any size-conditioned design as an engineering hypothesis to be validated, not established science.

## Key Findings

### The landscape has converged on a small number of architectural patterns

Across every tool and framework surveyed, the same three-part decomposition recurs: (1) a distinction between what is in the context window ("working memory," "main context," "short-term memory," "session state") and what is out of it ("archival," "external context," "long-term memory," "the store"); (2) a capture mechanism, either lifecycle-hook-driven or agent-tool-driven, that moves information from the former to the latter; and (3) an injection mechanism that brings a curated subset back. This maps cleanly onto the CoALA taxonomy the requester already intends to use, and onto MemGPT's OS-paging metaphor. The disagreements between systems are about WHERE synthesis happens (inline in the session versus an async external worker), WHAT triggers capture and compaction (token thresholds versus lifecycle events versus agent judgment), and HOW provenance and precedence are handled.

### Compaction is measurably lossy, and the losses fall on exactly the categories Smart Compact wants to protect

This is the strongest evidence base supporting the project's thesis. Multiple independent 2026 evaluations converge: heuristic summarization reliably preserves the "what" of a task (the dominant objective) while dropping the "how" (behavioral constraints, artifact trails, technical specifics). This is precisely the argument for structured state handoff.

### The when-to-compact question is where practitioner thinking is actively shifting

The field is moving away from pure capacity-triggered compaction toward task-boundary and handoff models. Anthropic's own guidance now says "when you start a new task, you should also start a new session." Sourcegraph retired compaction in its Amp agent in favor of "handoff." This is the live frontier and where Smart Compact's intent-driven triggering is most differentiated.

## Details

### Question 1: How production tools handle context management, compaction, and session state

**claude-mem (Alex Newman / thedotmack).** This is the most directly comparable system to Smart Compact, being a native Claude Code plugin rather than an MCP wrapper. Architecturally it hooks five lifecycle events (SessionStart, UserPromptSubmit, PostToolUse, Stop, SessionEnd) and captures tool usage automatically without the model choosing to record anything. This is the crucial architectural distinction its author draws against MCP-based memory: "plugins fire automatically on lifecycle events... while MCP servers sit idle until Claude decides to call them." Captured observations are compressed by a background worker using Claude's own agent-SDK (so synthesis is async and external to the interactive session, running on the user's existing Claude Code authentication rather than a separate key), stored in a local SQLite database with Chroma vector search, and injected at SessionStart. Retrieval at query time follows a token-efficient three-layer pattern: search an index, review IDs, then fetch full observations. It is a widely adopted project: roughly 89,500 GitHub stars (89,501 stars / 7,706 forks as of July 2026 per claudeskills.info's listing), having reached about 46,100 stars within weeks of launch. What it does NOT do: it captures observations (episodic tool-use traces) rather than maintaining structured state/process/preference meta-information, and its trigger for synthesis is lifecycle-event-driven passive capture, not intent-driven compaction. It is essentially an episodic-memory system, in CoALA terms.

**Mem0's Claude Code plugin.** Three components: an MCP server (nine memory tools: add, search, get, update, delete, etc.) pointed at Mem0's hosted cloud, a set of lifecycle hooks, and an SDK skill. The hooks fire at session start, context compaction, task completion, and session end. Two design choices are directly relevant to Smart Compact's question 5. First, provenance separation is built in: "What you type is stored as yours. What Claude produces (session summaries and compaction summaries) is stored as the assistant's, so its suggestions never become your stated preferences." This is exactly the user-authored-versus-assistant-produced distinction the requester wants to encode. Second, staleness policy is explicit and typed: on the PreCompact hook, Mem0 stores a summary of the current session with infer=False (storing it verbatim rather than re-extracting facts), and "session-state and compact-summary memories are automatically tagged with expiration_date = today + 90 days. Durable memory types like decisions, anti-patterns, and conventions stay unexpired." Mem0 also scopes memory into user-level (persists across all sessions), session-level (garbage-collected when the session ends), and agent-level (shared knowledge like codebase conventions). Notably, the plugin does NOT auto-inject memories before every response; it injects a decision rubric at session start and lets the agent decide when to search. In its April 2026 release, Mem0 reported: "On LoCoMo, Mem0 scores 91.6, a gain of 20 points... On LongMemEval, the score reaches 94.8, a gain of 27 points overall, with assistant memory recall specifically improving by 53.6 points," plus 64.1 on BEAM at 1M tokens, using single-pass ADD-only extraction with no agentic loops.

**Letta / MemGPT.** The foundational tiered-memory architecture. MemGPT (Packer et al., 2023, arXiv 2310.08560) frames the context window as RAM and external stores as disk, with the agent using function/tool calls to page information between them. Main context comprises read-only system instructions, a FIFO queue of recent conversation, and a writable scratchpad. When the context window fills, conversation history is compacted into a recursive summary stored as a memory block, while old messages remain retrievable via conversation_search. Letta (the productionized framework) implements three tiers: core memory (small, always-in-context, self-edited via memory_insert/memory_replace), recall storage, and archival storage. The defining property is self-editing: the agent decides what to save by calling memory functions during its reasoning loop. The tradeoff, as one comparison put it, is "predictability vs intelligence": self-editing is adaptive but "memory quality depends entirely on the model's judgment. If the model fails to save something, it's gone." This is a critical warning for Smart Compact's question 3, because model judgment is exactly what degrades with smaller models.

**LangGraph.** Cleanly separates two mechanisms that developers routinely conflate. Short-term memory is thread-scoped state persisted by a checkpointer, which saves the entire graph state after every node execution (enabling resume, time-travel debugging, crash recovery). Long-term memory is the Store, a persistent key-value system namespaced across threads, explicitly modeled on the semantic/episodic/procedural distinction. The consensus practitioner guidance is to treat these separately: "The checkpointer is infrastructure. Enable it... The Store is different. It's an application design problem where you need to decide what information is worth persisting, how it should be scoped, and when it should be removed." For compaction, LangGraph relies on message trimming or a summarize node before overflow. A limitation noted in a 2026 benchmark: LangGraph short-term memory is append-only and truncation is purely recency-based, so "contradictory or outdated information cannot be removed."

**Google ADK.** The most rigorous separation of concerns of any framework surveyed, and the closest to the requester's own decomposition. ADK splits Session (a conversation thread containing Events plus State), State (a structured key-value store), Memory (a long-term searchable knowledge store populated from completed sessions), and Artifacts (binary/large content stored by reference, not inline). The recurring failure mode it explicitly targets is "conflating 'History' (what was said) with 'State' (what is true)." State uses scope prefixes: no prefix (session-scoped), user: (across a user's sessions), app: (across all users), and temp: (never persisted, discarded after the turn). Memory is populated via add_session_to_memory and read via search_memory or a PreloadMemoryTool that always retrieves at the start of each turn. This is the cleanest existing model for the requester's state/processes/preferences decomposition.

**OpenAI's structured-state-object pattern.** The OpenAI Agents SDK cookbook on context personalization is the closest published match to Smart Compact's intended precedence design. It describes a state object as a "local-first memory store (structured profile + notes)," and a full lifecycle: distill memories during a run (tool call to session notes), consolidate session notes into global notes at the end (with dedupe and conflict resolution), and "inject a well-crafted state at the start of each run (with precedence rules)." On conflict handling: "If a user provides a new value for one of the fields in the profile, you can prompt the agent to use that as the latest information in the precedence rules for resolving the conflict." OpenAI separately published a March 2026 compaction feature in the Responses API and a cookbook ("Building Reliable Agents with Memory and Compaction") drawing the exact division Smart Compact should adopt: "compaction helps the current run continue, memory helps later runs start with useful workflow guidance."

**Anthropic's own guidance.** Several primary sources. The Claude Developer Platform now offers server-side compaction (compact_20260112 strategy) with a configurable token trigger and, importantly, a pause_after_compaction option that lets you inject additional content blocks (preserved recent messages, instruction-oriented messages) after the summary is generated but before the conversation continues. This pause-and-inject hook is architecturally significant for Smart Compact. Anthropic's "Effective context engineering" post (Sep 2025) describes Claude Code's compaction as passing message history to the model to summarize, preserving "architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," then continuing with the summary plus the five most recently accessed files. It also names the two other long-horizon techniques: structured note-taking (a NOTES.md the agent maintains outside context and re-reads, as in Claude playing Pokemon) and multi-agent architectures with fresh sub-agent context windows. The "Effective harnesses for long-running agents" post describes the shift-work problem directly: agents "work in discrete sessions, and each new session begins with no memory of what came before," solved with an initializer agent plus a coding agent that leaves "clear artifacts for the next session." It candidly admits compaction's limit: it "doesn't always pass perfectly clear instructions to the next agent." Claude Code's own hooks give the capture points: SessionStart (with source values startup/resume/clear/compact), PreCompact (with trigger values manual/auto, and custom_instructions), Stop, and SessionEnd. A documented caveat: SessionStart-injected text is saved in the transcript and replayed on resume, so time-sensitive values go stale, and text framed as system commands can trip Claude's prompt-injection defenses (write state as factual statements, not imperatives).

### Question 2: When to compact, trigger design

The old default was capacity-triggered: monitor token usage, fire a summarization turn near the limit. Every major system still supports this (Anthropic's input_tokens trigger, the Claude Agent SDK's compaction_control, LangGraph's summarize-before-overflow). But the thinking has shifted on three fronts.

First, there is a documented problem with capacity triggers specifically: the model is at its least capable exactly when it must compact. As one Anthropic-aligned guide put it, "due to context rot, the model is at its least intelligent point when compacting." A larger window buys time to compact proactively, but does not fix the underlying issue.

Second, task-boundary triggering is now the recommended discipline. Anthropic's April 2026 session-management guidance frames every turn as a branching point with the rule "New task, new session," and the operative question "is this current context still helping?" This is intent/goal-change triggering by another name, applied manually. Smart Compact's contribution would be to detect the boundary automatically rather than relying on the user to run /clear.

Third, and most concretely, the handoff model is displacing recursive compaction. Sourcegraph retired compaction in its Amp coding agent after finding that recursive summarization (summaries of summaries) distorted earlier reasoning as sessions accumulated compaction events. Handoff instead lets a developer specify a goal for the next phase, then extracts only the relevant information into a fresh context, "carrying forward only what still matters for the next stage." This is essentially intent-driven compaction and is strong external validation of Smart Compact's core design.

On detecting context degradation or ambiguity mid-session ("context rot" detection): this is largely aspirational. Chroma's "Context Rot" report (Hong, Troynikov, Huber, July 2025) established empirically across 18 models that performance degrades non-uniformly as input grows, but it measures degradation offline rather than providing a runtime detector. I found no production system that detects mid-session "confusion" or task-material ambiguity and triggers compaction on that signal. This is a genuinely open area and a possible differentiator, though also a research risk.

### Question 3: Model-size-dependent context degradation

This is the requester's suspected under-studied area, and that suspicion is correct. The evidence divides into solid benchmark data on degradation-versus-size and an almost total absence of strategy guidance conditioned on size.

**Effective versus advertised context length (RULER; Hsieh et al., NVIDIA, 2024, arXiv 2404.06654).** RULER defines effective length as the longest context at which a model stays above a quality threshold (Llama2-7B's 4K score of 85.6% on the 13-task average). The headline finding: "while all models claim context size of 32K tokens or greater, our results indicate that only half of them can effectively handle sequence length of 32K... almost all models fall below the threshold before reaching the claimed context lengths." Representative claimed-versus-effective pairs: Llama3.1-70B claims 128K, effective 64K; Llama3.1-8B claims 128K, effective 32K; Qwen2-72B claims 128K, effective 32K; Mistral-7B-v0.2 claims 32K, effective 16K; GLM4-9B claims 1M, effective 64K. Within a single family holding training constant, size helps: on the Yi family, "the 34B model is significantly better than the 6B model on RULER for both performance at length of 4K and the relative degradation."

**Critical caveat: the size trend is noisy and training-recipe-dependent.** RULER itself shows inversions where the compact GLM4-9B (effective 64K) outranks Qwen2-72B and Command-R-plus-104B (both 32K). The ProLong work notes RULER can show "unintuitive trends such as Gemini-1.5-Pro and Llama-3.1 (70B) perform worse than Llama-3.1 (8B)." So parameter count is a weak predictor relative to long-context training.

**NoLiMa (Modarressi et al., Adobe/LMU, 2025, arXiv 2502.05167)** strips lexical overlap so retrieval requires latent inference, and reveals far harsher degradation. Effective length (max length keeping 85% of the model's own short-context base): Llama3.1-8B effective 1K; Llama3.1-70B and Llama3.3-70B effective 2K; Gemma3-4B effective under 1K (collapsing to near-zero by 16K to 32K); Gemma3-27B effective under 1K. At 32K, ten of the evaluated models drop below 50% of their short-context baseline, and even GPT-4o falls from 99.3% to 69.7%. The scaling verbatim: "'lite' models such as Gemini 1.5 Flash, GPT-4o mini, and Llama 3.1 8B perform well in shorter contexts (under 1K tokens) but fail to generalize effectively in longer contexts." Note the sobering implication: on genuinely associative recall, even 70B to 405B models collapse to a couple thousand tokens of effective length. Externalization and small resident schemas are not a small-model concession here; they help every model.

**Instruction-following on injected structure (LIFBench; Wu et al., 2024, arXiv 2411.07037).** This is the most directly relevant benchmark for resident maps and state files. Its key finding cuts both ways for Smart Compact: "larger models generally are better at capabilities like 'Ori,' 'Num,' and 'Spat'... In contrast, format-related abilities are effectively managed even by smaller models, suggesting they are less dependent on model size." In other words, a small model can be trusted to follow a rigid format/schema, but its ability to recognize and reproduce the right content within that schema, and its instruction-following stability, degrade faster with length. Instruction-following stability worsens with length and improves with size, though instruction-tuning can override size (a 7B instruct model beat Llama-3.1-70B base on the stability metric). LOCA-bench (2026) gives frontier-versus-open numbers at length: Claude-4.5-Opus averaged 68.1 across lengths versus DeepSeek-V3.2-Thinking 42.7, MiniMax-M2.1 35.8, GLM-4.7 35.2, with all models declining steeply past 64K to 96K.

**Strategy guidance conditioned on size is essentially absent from research.** A targeted search found no peer-reviewed paper prescribing window size, compaction frequency, schema simplicity, or externalization aggressiveness as a function of model scale. What exists is practitioner heuristics: guidance for a coding agent that recommends leaning on precise inclusion patterns for small local models while affording broader context for large cloud models, and a Docker engineering note that "the smaller the model, the harder it will be to handle a large context and stay focused," recommending a /clear affordance. The best indirect research-grade evidence is the LIFBench format-versus-content split: it implies that for smaller models Smart Compact should keep injected schemas rigid and simple (format-following survives), externalize aggressively (recognition and recall degrade), and compact/refresh more frequently (stability degrades with length). But this is inference, not measurement.

**Practical answer to the requester's question.** If the same machinery must serve a Gemma-4-class local model and a frontier Claude model, the honest position is: the direction of the needed changes is clear (tighter effective windows, more aggressive externalization, simpler injected schemas, more frequent compaction for the small model), but the magnitudes are unmeasured, and raw parameter count is a poor dial because training recipe dominates. Smart Compact should expose these as configurable parameters and calibrate empirically per model rather than by a parameter-count formula.

### Question 4: Academic and research-framework grounding

**CoALA (Sumers, Yao, Narasimhan, Griffiths, 2023, arXiv 2309.02427).** The taxonomy the requester is using. Working memory holds active information for the current decision cycle; long-term memory splits into episodic (past experiences/events), semantic (facts about the world), and procedural (skills/how-to, often in code or weights). It structures the agent as memory modules plus an action space (external grounding actions plus internal reasoning/retrieval/learning actions) plus a decision procedure. One caveat worth encoding, from a 2026 critique: CoALA "does not distinguish the persistence semantics of semantic memory from episodic memory," treating both as long-term with no formal difference in update mechanism, ownership scope, or decay. This matters directly for Smart Compact: a stated preference (semantic, durable, should be superseded not forgotten) and a session experience (episodic, ephemeral, should decay) need different persistence mechanics even though CoALA files them together. This is exactly what Mem0's typed-expiry policy operationalizes.

**MemGPT** (covered under Letta above) is the canonical in-context/out-of-context tiering paper.

**Knowledge-graph memory: Graphiti/Zep and HippoRAG.** Zep (Rasmussen et al., 2025, arXiv 2501.13956) is powered by Graphiti, a temporally-aware knowledge graph with three subgraphs (episode/raw data, semantic entity, community summaries) that mirror episodic/semantic memory. Its distinguishing mechanism is bi-temporal modeling: every edge carries validity intervals (t_valid, t_invalid), and when new knowledge contradicts old, "it doesn't throw the old fact away... it uses the timestamps to mark it as superseded, preserving history." It reports 94.8% versus MemGPT's 93.4% on the Deep Memory Retrieval benchmark and up to 18.5% gains with 90% lower latency on LongMemEval. This bi-temporal supersession is the rigorous version of the requester's preference-staleness problem. HippoRAG (Gutierrez et al., NeurIPS 2024) uses Personalized PageRank over an LLM-extracted knowledge graph to do associative, multi-hop retrieval, outperforming conventional RAG by up to 20% on multi-hop QA at 10 to 20x lower cost than iterative retrieval; HippoRAG 2 adds passage nodes and query-to-triple linking. These are almost certainly out of scope for Smart Compact v1 (they solve large-corpus retrieval, not session handoff) but are the reference designs if durable semantic memory grows large enough to need graph retrieval.

**Recursive summarization: RAPTOR (Sarthi et al., ICLR 2024, arXiv 2401.18059).** Recursively embeds, clusters, and summarizes chunks bottom-up into a tree with multiple abstraction levels, retrieving from the appropriate level; improves QuALITY by 20 absolute points. Relevant as the canonical recursive-summarization design, and as a caution: a follow-up (Ou and Lapata, 2025) shows "hierarchical merging can amplify hallucinations during recursive summarization," which is the same recursive-distortion failure that drove Sourcegraph off compaction.

**Published evaluations of compaction quality: the strongest new evidence for the project.** Several 2026 results directly measure what heuristic summarization loses:

- "Lost in Compaction" (arXiv 2608.11242) defines Session Constraints (SCs) as user instructions that constrain HOW a task is done ("confirm with me before taking any action") rather than what it is, and shows they are "silently dropped during compaction." Its CompInt suite finds, verbatim, "current compactors retain only 17% of injected SCs on average, and most perform worse than running the same task without compaction." An SC-aware extractor running alongside the compactor is "achieving over 90% retention across all three scenarios." This is the single most important external result for Smart Compact: it is empirical proof that the preferences/processes layer is exactly what heuristic summarization destroys, and that a dedicated extractor fixes it.
- Factory.ai's probe-based framework (reported via Factory's docs and Tessl coverage) scores compaction on six dimensions (accuracy, context awareness, artifact trail, completeness, continuity, instruction following) 0 to 5, using GPT-5.2 as the LLM judge "following the methodology established by Zheng et al. (2023) in their MT-Bench paper," over 36,000+ messages from real engineering sessions. The critical weakness is artifact tracking: "all methods scored low on tracking which files were created/modified/examined (Factory's best was 2.45/5), suggesting this may need dedicated state tracking beyond summarization." On the artifact probe specifically ("Which files have we modified?"), Factory scored 3.6 while OpenAI scored 2.8, because "OpenAI's compression discards file paths as low-entropy content." On overall score, Factory's structured summarization reached 3.70 versus 3.44 for Anthropic's SDK compression and 3.35 for OpenAI's compact endpoint. The takeaway for Smart Compact is direct: artifact/state tracking needs dedicated structured capture, not summarization.
- SentinelOne's malware-analysis evaluation found compaction cut input tokens by about 86% "with no measurable change to the aggregate evaluation score," but with one dimension declining: domain object modeling (recovering higher-level structures). Their operative principle matches the project's: "compaction handles working memory and durable storage handles facts."
- Factory.ai's separately reported finding that aggressive compression (99.3% token reduction) actually increased total cost because the agent re-fetched forgotten information reframes context management as a correctness problem, not a token-minimization problem.
- Standardized open evaluation is still missing. As one 2026 survey notes, "a standardized open-source evaluation harness for compaction quality across the six dimensions... does not yet exist," and most benchmarks test only a single compaction event rather than the recursive chains that cause real degradation. Letta's Context-Bench (Oct 2025) targets chained file operations and multi-step decision consistency, the closest available proxy.

### Question 5: Design patterns and failure modes to encode

**Provenance separation.** Mem0's Claude Code plugin already implements the exact pattern: user-typed content is stored as the user's, assistant-produced summaries as the assistant's, "so its suggestions never become your stated preferences." Smart Compact should adopt this as a first-class tag on every memory item. There is also a security dimension: Palo Alto Unit 42 demonstrated indirect prompt injection planting malicious instructions into an agent's persistent memory via a compromised webpage, so provenance is also a trust boundary, not only a semantic one.

**Expiration and staleness.** Mem0's typed policy is the reference: session-state and compaction summaries expire on a fixed horizon (today + 90 days), while decisions, anti-patterns, and conventions never expire. A cleaner general framing from Mem0's cookbook: tiered retention with short windows for session context, longer for chat history, none for preferences, because "when 'User prefers dark mode' competes with 'Currently browsing electronics' from 6 months ago, semantic search returns stale session data instead of actual preferences." Graphiti's bi-temporal supersession is the more sophisticated alternative when you need to preserve history rather than delete.

**Write rules (what belongs where).** The ADK scope-prefix model (session / user / app / temp) and Mem0's scope levels (session / user / agent) both encode this. The consistent warning: "If you store architectural decisions at session scope, the agent forgets them the next time it runs." Smart Compact needs an explicit routing rule mapping state and process to session scope and durable decisions/preferences/conventions to permanent scope, matching its CoALA episodic/procedural/semantic decomposition.

**Precedence ordering.** OpenAI's cookbook is the working reference: inject state with explicit precedence rules and resolve conflicts in favor of the newest user-provided value. The requester's intended ordering (current instruction > session-specific > general preference) is consistent with this and with the "Lost in Compaction" finding that session constraints must survive as a distinct, high-priority layer.

**Inline per-turn synthesis versus async passive capture.** This is the central cost/quality tradeoff and the systems split cleanly. claude-mem uses async external workers (a background process compresses observations, keeping the interactive session fast and cheap). Letta uses inline agent-driven self-editing (adaptive but dependent on model judgment and adding tokens/latency to every turn, and lossy if the model forgets to save). Mem0 uses passive capture with async extraction and injects a decision rubric rather than synthesizing every turn. The evidence favors async external synthesis for Smart Compact: it keeps the interactive model's attention budget focused on the task, avoids adding synthesis tokens to a context that is already under pressure, and, critically for question 3, does not rely on the (possibly small, possibly degrading) session model to make good save decisions mid-task. The synthesis model and the working model can even differ.

## Recommendations

**v1 scope, staged.**

Stage 1 (adopt, do not build): Wire the capture layer to Claude Code's existing lifecycle hooks (SessionStart, PreCompact, Stop, SessionEnd, PostToolUse), mirroring claude-mem's proven hook set. Use Anthropic's pause_after_compaction API hook as the injection point for structured state at the compaction boundary, since it exists precisely to add instruction-oriented content after the summary. Adopt Mem0's provenance tagging (user-authored versus assistant-produced) and typed expiry (durable versus session-scoped) wholesale rather than reinventing them. Use ADK-style scope prefixes for the state/process/preference routing.

Stage 2 (build the differentiator): Implement the structured state/process/preference object as a distinct, high-priority injected layer that survives compaction verbatim, directly targeting the "Lost in Compaction" failure (17% constraint retention). Run synthesis in an async external worker, not inline, to protect the interactive attention budget and to decouple synthesis quality from the working model's size. The measurable success criterion is session-constraint retention across a compaction boundary; aim to move from the roughly 17% baseline toward the 90%+ a dedicated extractor achieves. Separately, treat artifact/state tracking (which files were touched, which decisions made) as dedicated structured capture rather than trusting it to summarization, since even Factory.ai's best method scored only 2.45/5 there.

Stage 3 (the research frontier, gated on evidence): Intent-driven / task-boundary triggering. Start with the low-risk version validated by Sourcegraph's handoff and Anthropic's "new task, new session" guidance: detect explicit task transitions and offer a goal-specified handoff. Defer automatic mid-session "context rot / confusion" detection until you have an offline metric that reliably fires, because no production system does this yet and the false-positive cost (compacting mid-task) is high.

**Thresholds that would change the plan.** If your own probe-based evaluation (build one; Factory's six-dimension scheme is the template) shows structured handoff beating Claude's native compaction on artifact-tracking and constraint-retention by a wide margin, prioritize replacing rather than augmenting native compaction. If it does not, position Smart Compact as an augmentation layer that rides Anthropic's native compaction via the pause-and-inject hook, which is far less engineering. For the model-size question, calibrate empirically: measure effective context length and constraint retention per target model (RULER-style and CompInt-style), and set window size, compaction frequency, and schema complexity from those measurements rather than from parameter count, because the benchmarks show parameter count is a noisy predictor.

**What is already commoditized and should be adopted, not built:** lifecycle-hook capture, SQLite/vector local storage, provenance tagging, typed expiry, scoped state, async compression workers, and precedence-on-inject. All of these have reference implementations in claude-mem, Mem0, ADK, and the OpenAI cookbook.

**What remains genuinely open (and is where the project can contribute):** automatic intent/task-boundary detection for compaction triggering; mid-session context-degradation detection; reliable preservation of session-scoped behavioral constraints across compaction (partially solved by the "Lost in Compaction" extractor, not yet in any Claude Code product); dedicated artifact/state tracking beyond summarization; a standardized open evaluation harness for compaction continuity; and model-size-conditioned strategy, which is unmeasured.

## Caveats

The strongest evidence in this survey is on the losses caused by heuristic compaction (multiple converging 2026 evaluations) and on the reality of context rot (Chroma, and every long-context benchmark). These are solid.

The weakest area, exactly as the requester suspected, is model-size-conditioned strategy. There is good benchmark data showing smaller models degrade earlier, but it is noisy, dominated by training recipe rather than parameter count, and there is essentially no research prescribing how context management should change with size. Every size-conditioned recommendation in this report is engineering inference from adjacent benchmarks (RULER, NoLiMa, LIFBench), not a measured result. Treat it as a hypothesis to validate per model.

Several of the most useful practitioner findings (Sourcegraph's handoff, Factory.ai's probe evaluation, SentinelOne's token-reduction numbers) come from company blogs and secondary coverage rather than peer-reviewed work; they are credible and consistent with each other but have not been independently replicated.
